HOI4 文本、图标覆盖与 Lua 主导加载框架可行性分析
================================================
2026-10-02，针对 F:/SteamLibrary/steamapps/common/Hearts of Iron IV 的本机安装。

结论
----
不写入游戏安装目录，仍然改变原版文本、图标或在原版界面上增加信息，是可行的。
Lua 主导的构建、组合和加载框架也是可行的工程方向，最先应实现外部 Lua 编译与语义补丁。
纯 Lua 全面接管游戏运行时、所有原功能无损兼容、性能与能力全面超过原方式，目前没有证据支持。
研究阶段完成静态分析；随后已实现独立的外部 Lua 构建原型，见 原型实施与验证.txt。
原型未注册或启用，没有接入本项目当前的科技、文本或图标。引擎内运行时加载器仍未实现。

三种“不修改原版”的区别
----------------------
1. 不写入 Steam 安装目录：普通 Mod 已支持。Mod 可让引擎读取其他文件或同名键。
2. Mod 也不放原版同名源文件：许多文本、Sprite、Scripted GUI 可独立新增或按键覆盖；任意数据库字段的通用补丁尚未发现官方接口。
3. 不改变游戏进程：外部编译框架与普通 Mod 可满足；运行时原生桥接若需要挂钩，则不满足这一条件。
框架必须如实显示它用了哪种方法，不能把“自动生成一个原版同路径替代文件”称为完全没有覆盖原版。

一、文本与图标怎么放在原版内容之上
--------------------------------
文本：在 Mod 的 localisation/replace/ 下放一个独立 *_l_simp_chinese.yml，使用需要覆盖的同名本地化键。
文件采用 UTF-8 BOM，首行为 l_simp_chinese:；只列出要改的键，不复制整个原版本地化文件。
例如 basic_medium_tank_chassis_desc 可以只改描述，NSB_armor.txt 不需要跟着修改。
外部框架还可在构建时读取当前原文，输出“原文 + 附加说明”，避免手工维护整段旧翻译。
同名键里的 $同名键$ 不应被当成读取旧值的继承语法；构建器需要先捕获底层值再输出最终值。
同一层多个 Mod 的键冲突仍需明确优先级或报冲突，replace 文件夹不会自动解决语义冲突。
Kaiserreich 源码在 localisation/replace/frontend_l_english.yml 中展示了独立文件覆盖原版键的实际使用。

图标：有两个常用入口。
一是在 Mod 中放与原纹理相同虚拟路径的 DDS/TGA，让资源路径被覆盖；安装目录纹理仍保留。
二是在独立 interface/*.gfx 中定义需要的 Sprite，并通过加载优先级使用期望的定义。
例如原版 interface/Technologies.gfx 中 GFX_basic_medium_tank_chassis_medium 指向
gfx/interface/technologies/generic_medium_tank_chassis_1.dds。
若替换这个公用键，会影响所有使用它的界面，包括装备的后备图标；本项目之前的坦克图案问题就是需要避免的作用范围。
为幻想乡专用型号使用独立 GFX 名称，或在支持国家后备入口的界面使用对应国家键，可缩小影响范围。
国家键不是任意界面都支持的统一条件选择器，不能保证仅靠给键加国家前缀就能解决所有场景。

若“上面”指视觉上的覆盖层，可以用独立 GUI 容器 + common/scripted_guis/*.txt 挂到原版窗口。
原版 common/scripted_guis/_documentation.md 明确列出 technology_tab、production_tab、tech_armor_folder 等 parent_window_token。
它也支持 visible、按钮 effects、图标 image、元素 x/y 等属性。
因此可以在装甲科技页增加“幻想乡配件研发说明”面板及独立图标，原科技树定义和原界面文件无需完整复制。
这不等于自动给每个引擎生成的科技按钮、工具提示、自动效果列表插入条目。
缺乏可用挂载位置或单个节点需要结构变更时，仍可能要生成 GUI 替代文件；布局、点击穿透、滚动与 DPI 需实测。
科研真正解锁模块的逻辑也不会因为显示了文本或图标而自动改变。

二、本机文件和二进制实际发现
--------------------------
完整目录清点为 59,285 个文件，包括 DLC、工具、离线 Wiki 和额外归档，不能等同于 59,285 个官方游戏核心文件。
其中 DDS 32,275、TGA 6,774、TXT 4,875、YML 2,104、GUI 477、GFX 401、Lua 8。
本机另有第三方启动组件和额外文件，尚未与官方发行清单校验真实性；结论限定于本轮指纹对应的文件。

hoi4.exe：55,778,424 字节，PE32+，Machine 0x8664，6 个节，启用 ASLR 和 NX 标记。
SHA-256：7dc947be34970da1e1c787bcddbe7f62b610ff258aebf8f06aa8b348f3a031d5。
节包括 .text、.rdata、.data、.pdata、.rsrc、.reloc；CodeView 数据引用 hoi4.pdb，这并不表示 PDB 本体已取得。
PE 版本资源只给出 1.0，不能用它可靠判断游戏补丁版本；应结合游戏版本、hoi4_rev.txt 和二进制哈希。
本机 hoi4_rev.txt：c01a3d507f10bd8c713e88234de69ca110618138。

Lua 证据：
二进制 .rdata 中出现 Lua 5.1.1 / Lua 5.1、pdx_lua.cpp、LUA_PATH、LUA_CPATH 及 luabind 主线程校验消息。
licenses.txt 也明确列出 Lua 5.1.1 与 Luabind 0.9.1。
原版 common/defines/00_defines.lua 的 NDefines 表和诸多“no lua object named NAI”等诊断说明 Lua 配置读取与引擎相连。
这足以支持“该构建含 Lua / luabind 组件”，不能仅据字符串就证明任意 Lua 回调、DLL 模块或游戏对象都能供 Mod 使用。

8 个 Lua 源文件为 common/defines 的 3 个文件和 script/ 的 5 个文件。
script/autoexec.lua 注释声称启动后执行，但同时写有 package.path 修改当时不可用的备注。
该文件引入外交示例；utils.lua 中存在直接 OS/文件 I/O 辅助函数。
二进制 ASCII 查找没有 autoexec 或 00_defines 的完整字符串。路径也可能动态构造，未找到不等于不会执行。
这些脚本是否仍被当前 HOI4 路径调用、外交示例是否实际触发，必须通过启动时与运行时探针确认。
不能把发行目录里保留的脚本直接视为完整、有效的当前 Lua SDK。

虚拟文件系统证据是本轮最值得继续的发现：
hoi4.exe 有 110 个命名导出，其中 108 个为带 MSVC 修饰名的 PHYSFS_*。
导出包含 PHYSFS_mount、PHYSFS_mountMemory、PHYSFS_mountIo、PHYSFS_openRead、PHYSFS_registerArchiver、PHYSFS_getSearchPath。
相应导出指向本 EXE 中的 RVA，而非 PE 导出转发器。
相关字符串还包括 virtualfilesystem_physfs.cpp、virtualfilesystem.cpp、replace_path、CVirtualFile。
在此指纹下，PHYSFS_mount 的 RVA 为 0x24f4750，PHYSFS_mountMemory 为 0x24f4900。
这些只是研究证据，不应硬编码为跨版本调用地址；ASLR 下 RVA 与进程绝对地址也不是同一值。
PhysFS 官方文档明确提供目录、归档、内存归档挂载以及搜索路径前置功能。
因此，“让引擎优先读取一个组合好的虚拟资源层”有真实的实现基础。

限制也有直接证据：此构建还导出 PHYSFS_freezeConfig，可能有配置冻结机制，具体调用时序尚未反汇编确认。
导出是 C++ 修饰符号，不能默认与下载的上游 PhysFS C ABI 完全一致。
Lua C API 的 lua_* / luaL_* 没有作为命名导出出现；导入 DLL 中也没有独立 Lua DLL。
结合许可证和字符串，静态链接 Lua 是合理推测，但仅凭导入表不能证明全部实现方式。
没有导出 Lua API，不代表内部函数不存在；意味着外部模块不能直接假设有一套稳定、公开的入口可绑定。
PDXSDK.dll 中可见账号、Playset、已安装 Mod 等 SDK 符号；这些并不能证明它提供装备、科技或战斗数据库的运行时编辑 API。

资产样本：
NSB_armor.txt 是 41,790 字节的 Clausewitz 文本，GUI/GFX 是同类花括号数据描述，不是 Lua。
YML 为游戏约定的本地化格式，不能默认用通用 YAML 写出所有细节。
基础中型底盘 DDS 的尺寸为 173 x 77；DDS 头含格式字段，简单改扩展名不会变成正确图案。
map/provinces.bmp 为 5632 x 2048、24 位；地图需要图像与省份定义和索引共同一致。
所查 .mesh / .anim 样本以 @@b@ 开头，属于 PDX 二进制资产；本轮未解码其内部块。
字体样本 Arial12.fnt 是文本描述，ZIP 和 7z 样本有各自归档头。
一个通用加载器应允许这些二进制资源按字节透传，而不是试图把一切转换成 Lua 表。

三、建议分两层建设
----------------
A. Lua 主导的开发、构建和组合框架：可立项。

Lua 内容包 -> 读取原版/已启用 Mod 的有效底层内容 -> 有序语义补丁 -> 校验和冲突报告
            -> 生成用户目录中的组合 Mod / 缓存包 -> 原版引擎正常读取。

Lua 负责模块声明、条件、数据复用、循环生成、包依赖、补丁策略和构建流程。
Clausewitz 无损语法树负责精确定位并编辑节点，保留重复键、顺序、比较运算符、注释和未识别内容。
写出路径只位于用户缓存或 Mod 目录，不触碰游戏安装目录。
既有 Mod 文件与二进制素材支持原样透传，这比要求所有旧 Mod 转写 Lua 更接近完整兼容。
GUI、本地化、GFX、defines、地图/模型资源应分别有适配器；不能用一个简单字典合并所有格式。

例如 Lua 可以表达“给 basic_medium_tank_chassis 的效果列表追加某个许可提示”，
编译器针对本机当前科技文件生成最终组合文件，而作者不再手工复制整份 NSB_armor.txt。
如果引擎没有该字段的合并入口，输出仍会按相同虚拟路径替代该科技源文件。
这满足不写原版安装文件，改善多人修改同文件的冲突；不满足完全零原版定义覆盖。
若只是说明文字、独立图标和旁边的配件研发面板，应先用本地化/Sprite/Scripted GUI，避免生成科技替代文件。

与当前开发方式相比，明确可争取的优势：
按对象/字段合并补丁、同一文件多个修改集中组合、依赖拓扑排序、清楚显示生效来源、自动版本差异检查，
生成数百个装备与多语言文案、校验引用、缓存未变动产物、构建输出可重现、回滚组合包。
本项目现有 CJS 迁移器已提供可复现生成、哈希保护和多项校验；这些经验可迁移到 Lua 作者层。
Lua 本身不会让原版 C++ 战斗计算更快。性能改善需要测量，例如冷启动与增量构建时间，而不能先承诺全面胜出。

B. 可选原生桥接 + Lua 游戏运行时：有研究价值，尚不具备完成条件。

需要一个原生宿主，让 Lua 通过明确的接口操作资源层与允许操作的游戏状态。
PhysFS 导出有望支持内存资源包或自定义归档，但还要验证引导方式、挂载时机、配置冻结、搜索顺序和缓存失效。
挂载文件只解决“读到哪些字节”；不自动解决数据库已经装载、已建装备对象、科技效果缓存和 UI 状态的问题。
运行时每日回调、存档序列化、对象生命周期、主线程、联网确定性必须有各自机制。
原版脚本 API 未暴露的战斗算法或对象类型若要扩展，需要额外针对引擎的桥接/挂钩研究。
这类扩展即使不写磁盘上的 EXE，也可能改变游戏进程；版本适配与稳定性义务会显著增加。
单纯覆盖 script/autoexec.lua 或把 luaopen_* DLL 放到某处不能作为已验证的通用加载方案。

四、功能覆盖的真实边界
--------------------
原版文本、Sprite、贴图：普通 Mod 已可覆盖；可用 Lua 构建更明确的规则。
原版窗口旁的附加界面：支持的 Scripted GUI 挂载位可用；任意内部节点仍须逐项验证。
科技、国策、事件、装备等原有数据功能：Lua 构建后仍由原版语法和引擎执行，目标是完整输出能力。
模型、动画、地图、音频：原样资源透传与对应文本适配可保留既有能力；资源内容正确性仍需专门验证。
多个 Mod 精确合并同一对象：自定义编译器可以改善；逻辑相互矛盾的 Mod 仍需用户选择或明确兼容补丁。
Lua 任意每日逻辑：尚无已验证的通用游戏 Lua 回调入口；可编译为原版 on_actions/effects 的逻辑需遵守其能力边界。
新增硬编码战斗行为：不能靠换语言或挂载素材自动获得，需要原生桥接与针对具体行为的验证。
所有旧存档、多人同步、跨版本百分之百兼容：不能预先保证；数据库和代码变化需要迁移和版本测试。

五、下一步的可验收顺序
--------------------
第一阶段：外部 Lua 构建原型，只覆盖描述、独立图标和科技页附加面板，安装目录哈希保持不变。
第二阶段：以 NSB_armor.txt 为组合测试集，让两个内容包修改不同节点，验证原生科技解锁和既有字段无丢失。
第三阶段：扩展文本适配器与二进制透传，建立加载顺序、冲突、语言、DLC、分辨率和联网输出一致性测试。
第四阶段：单独验证本机 PhysFS 的搜索路径和挂载时机，以及实际 Lua 上下文和存活绑定。
只有第四阶段通过，才值得把运行时桥接列为可交付能力。

完整功能兼容至少需要原版与若干真实旧 Mod 的加载回归集、所有相关格式适配、真实引擎冷启动与开局验证。
原版文件层面能读取某文件，不足以证明里面每个数据对象的行为正确；不能再仅凭静态检查宣布实机成功。

证据、复现和未完成事项
--------------------
运行 node tools/research_hoi4_loader.cjs 可重新生成《原版文件与二进制审计.json》。
本轮解析 PE 头、节、导入、命名导出和指向位置、调试目录、ASCII/UTF-16 字符串及资源头。
检查前后 hoi4.exe 与 PDXSDK.dll 的 SHA-256 一致，工具对安装目录只读。
未做反汇编控制流分析、动态调试、内存读取、挂钩、注入或引擎内覆盖实测；未实现 Lua 宿主。
这是一份可行性研究与架构建议，不是已经存在且保证完全兼容的新加载器。
